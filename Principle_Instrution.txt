**Game Engine:** Godot 4  
**Programming Language:** GDScript  
**Game Category:** 2D Grid-Based Logic Puzzle  
**Platforms:** Android and iOS  
**Target Regions:** America, Europe, Africa and Middle East  
**Development Approach:** Solo developer with AI-assisted development.

### Core Game Concept

Chain Escape is an arrow-based logic puzzle.

The game board contains arrows pointing in four directions:

- Up
- Down
- Left
- Right

The player must identify the correct sequence of arrows to remove and clear the board.

Core gameplay includes:

- Grid-based puzzle boards.
- Directional arrows.
- Exit-path detection.
- Arrow removal animations.
- Logical dependencies between arrows.
- Level progression.
- Increasing puzzle difficulty.

Some arrows depend on other arrows. A dependent arrow can only exit after its required prerequisite arrows have been removed.

Keep the initial game focused on these mechanics. Do not introduce unnecessary gameplay systems without approval.

# 4. SOFTWARE ENGINEERING PRINCIPLES

These principles are mandatory for every script, scene and system.

## 4.1 SOLID Principles

**S — Single Responsibility Principle**

Every script and component should have one clear responsibility.

For example:
- Arrow handles its own visual representation and interaction.
- Board manages board state.
- Dependency manager evaluates prerequisites.
- Level manager handles level progression.

Do not combine unrelated responsibilities into one script.

**O — Open/Closed Principle**

Design systems so they can be extended without unnecessarily modifying existing working logic.

For example, adding a new arrow type should not require rewriting the entire board system.

**L — Liskov Substitution Principle**

If inheritance is used, derived classes must behave consistently with their parent contracts.

Do not create inheritance relationships that break expected behavior.

**I — Interface Segregation Principle**

Prefer small, focused interfaces and signals over large components that depend on unrelated functionality.

**D — Dependency Inversion Principle**

High-level systems should not become tightly coupled to low-level implementation details.

Use appropriate signals, resources and clearly defined responsibilities.

Do not introduce abstractions where simple composition is sufficient.

## 4.2 DRY — Don't Repeat Yourself

- Do not duplicate gameplay logic.
- Extract genuinely reusable functionality.
- Centralize shared configuration.
- Reuse scenes and components.
- Avoid maintaining multiple copies of the same rules.

However, do not create unnecessary abstractions just to eliminate a few repeated lines.

## 4.3 KISS — Keep It Simple

- Prefer straightforward solutions.
- Avoid unnecessary frameworks.
- Avoid excessive design patterns.
- Avoid premature optimization.
- Keep gameplay logic understandable.
- Do not over-engineer simple features.

## 4.4 Separation of Concerns

Keep these responsibilities separate:

- Gameplay logic.
- UI presentation.
- Game state.
- Level data.
- Level generation.
- Save management.
- Audio.
- Configuration.
- Input handling.

A UI component should not independently implement core puzzle-solving rules.

## 4.5 Clean Architecture

- Create a meaningful project structure.
- Keep dependencies understandable.
- Avoid circular dependencies.
- Keep components modular.
- Make systems independently testable where practical.
- Avoid oversized scripts or God Objects.

## 4.6 Human-Readable Naming

Use descriptive names for:

- Files.
- Variables.
- Functions.
- Classes.
- Signals.
- Constants.

Good:
`check_arrow_exit_path()`

Bad:
`check()`

Good:
`remaining_arrow_count`

Bad:
`rac`

Avoid cryptic abbreviations and single-letter variable names, except standard loop indices when appropriate.

## 4.7 Strict Typing

Use GDScript static typing wherever practical.

Examples:

- Explicit variable types.
- Typed function parameters.
- Explicit return types.
- Enums for fixed states.
- Appropriate custom classes and resources.

Avoid unnecessary use of untyped variables and Variant values.

Use type-safe data structures and validate incoming level data.
